# 执行与调度优化记录

2026-11-10。功能基线为 `4d385cd`，比较同一宿主上的改前/改后实现。宿主为 Windows x64、Intel i5-13600KF。数据来自独立宿主基准，不包含 Skyrim、Papyrus VM 或 RaceMenu 的实际执行时间。

## 已落实的改动

| 路径 | 原有成本 | 当前处理 |
| --- | --- | --- |
| 菜单每帧读取 | 深拷贝角色数组、显示名和诊断字符串 | 持有 `shared_ptr<const MenuSnapshot>`，一次读取覆盖整帧；发布方仍构建独立不可变快照 |
| 保存快照与序列化校验 | 每个区域为最多五层建立哈希集合 | 在连续的小数组内比较 ID；保存过滤继续保留第一个有效同 ID 层及原有顺序 |
| 调度单项取出 | 为单个 deadline 构建临时 vector，空业务队列也 reserve | `popDue` / `popDueSteady` 返回 optional，取出阶段无临时分配 |
| 多时钟到期积压 | 直接比较游戏小时与活动秒的原始数值，业务期限先耗尽预算 | 各域内部按 due 排序，日历/活动域轮换；Runtime 交替处理业务与 steady 项，沿用总条数和墙钟预算 |
| P+ 连续查询 | 回调完成后等下一次 50ms poll 才派发下一步骤 | 回调更新完状态后请求 BackgroundPump；VM 派发仍由游戏线程执行，保留 50ms 超时/取消轮询 |
| NPC 菜单候选 | 需要扩大可测试角色范围 | 显式刷新时扫描并排序去重，常规 pump 复用连续值缓存 |
| Overlay 槽位处理 | 新层可能先占旧层槽位，分配与应用重复读材质 | 先保留选中层旧槽，再分配新槽；一次 reconcile 复用连续槽位快照 |

全量保存快照仍按当前活动时间更新，因为 `timedClearRemainingSeconds` 随时间减少。仅按图层 revision 缓存整份结果会冻结倒计时。角色表保留按 ActorId 查询的哈希结构，区域内最多五层使用连续比较；两种访问方式各有对应的数据结构。

## 测量

### 菜单读取

`tools/bench_menu.cpp`：每个显示名 64 字节，先发布一次，再读取 5,000 次；分配计数不包括发布。Clang C++23，`-O2 -DNDEBUG`。

| 角色数 | 改前分配 | 改后分配 | 改前总时间 µs | 改后总时间 µs |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 85,000 | 0 | 3,643 | 76 |
| 256 | 1,285,000 | 0 | 39,014 | 76 |
| 1,024 | 5,125,000 | 0 | 258,515 | 76 |

这里测的是快照读取，不是完整菜单帧；收益来自移除与角色数成正比的复制。

### 保存快照

`tools/bench_persistence.cpp`：1,024 个角色，每人 7 区域、每区域 5 个有效层；15 轮，每轮 8 次，统计每次快照。相同探针分别链接基线与新实现，Clang-CL `/O2 /DNDEBUG`。

| 指标 | 改前 | 改后 |
| --- | ---: | ---: |
| 每次 C++ heap 分配 | 57,345 | 7,169 |
| 中位耗时 µs | 4,179.6 | 854.8 |
| P10–P90 µs | 3,816–4,466 | 781–923 |

该样本分配减少 87.5%，中位耗时约为原来的 20.5%。保留下来的分配主要是快照本身的角色、区域图层存储。

### 调度器

单项取出循环的 C++ heap 分配计数，不包括插入期限：

| 已到期项数 | 改前临时分配 | 改后临时分配 |
| ---: | ---: | ---: |
| 0 | 1 | 0 |
| 1 | 2 | 0 |
| 256 | 257 | 0 |

跨时钟回归同时插入日历域到期值 1–300、活动域到期值 1,000,000–1,000,299，各 300 项；当前时间为游戏小时 1,000、活动秒 2,000,000。在 256 项预算下，旧实现取出 256 个日历项、0 个活动项，新实现各取出 128 项，并保留各域内部到期顺序。

### Overlay

隔离 stub、Body 五层、六槽：首次 reconcile 的 `GetNodeOverride` 从 42 次降为 29 次，`HasNodeOverride` 从 5 次变为 6 次。稳定目标再次 reconcile 为 20 次 Get，其中新增的五次 alpha 校验用于识别外部材质漂移。新回归逐项删除 diffuse/normal/specular 或改变 alpha，确认相同 revision 可以修复；追加层只写新槽，已有层的材质保持不变。

这些是外部接口调用数，没有据此推算游戏帧率或缓存命中率。P+ callback 到下一次派发的实际延迟也需在游戏里测量。

## SIMD、AVX2 与 FMA

当前可定位的成本是分配、少量离散键比较、容器访问和 VM 等待。每区域最多五层，尚无足够大的连续数值内核适合手写向量化。此次优先减少工作量和数据搬运，编译目标继续沿用现有设置。

若后续采样定位到批量数值内核，可把该内核单独向量化并做 CPU 特性分派。全局 `/arch:AVX2` 会允许编译器在普通路径生成扩展指令；微软说明应在执行前确认处理器支持。[MSVC x64 指令集选项](https://learn.microsoft.com/en-us/cpp/build/reference/arch-x64?view=msvc-170)。FMA 会把运算合并，浮点结果约束应与性能一起验证；此次不改浮点编译模型。[MSVC 浮点行为选项](https://learn.microsoft.com/en-us/cpp/build/reference/fp-specify-floating-point-behavior?view=msvc-170)。

## 协程与回调的取舍

纯定时工作继续以 deadline 数据表示：更新、取消、epoch/revision 检查都集中在 Scheduler/Runtime，暂停与游戏时间属于显式时钟域。给每个计时器增加协程帧并不能消除这些规则，也没有减少当前调用层次。

P+ 的多步骤查询适合线性 `co_await` 语法，但仍需 Papyrus awaitable、游戏线程恢复队列、超时/取消传播和晚到 callback 的 token 检查。当前状态机已经承担这些职责；本轮用回调唤醒消除固定轮询带来的额外等待，保留现有生命周期模型。这里的决定基于维护结构，不把协程本身视为性能问题。微软也说明协程帧通常由编译器分配，并在能证明生命周期时消除分配。[微软协程实现说明](https://devblogs.microsoft.com/cppblog/std-generator-standard-library-coroutine-support/)。

## 复跑

从仓库根目录，用 C++23 优化构建运行 `tools/bench_menu.cpp`、`tools/bench_persistence.cpp`，分别链接 `src/menu/MenuState.cpp`、`src/persistence/SerializationCodec.cpp`。基准源码同时兼容基线和新接口；基线取 `4d385cd` 对应实现。基准程序不加入插件，也不进入发布包。

常规验证：`xmake build -y -a` 后运行全部 `slacs_*_checks`。基准时间会受宿主负载、编译器和分配器影响；分配次数与业务结果是这次比较的主要依据。
